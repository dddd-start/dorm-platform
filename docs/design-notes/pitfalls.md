# 真实踩过的坑（17 个）

> 来源：`docs/agent-sse-design.md`、`docs/parity.md`、`docs/verification.md`、git log，以及源码注释里带编号的缺陷记录（H*/M*/P*）。
> 每条四段：**现象 → 定位 → 修复 → 可复用排查法**。第三、四段是重点——定位方法与可复用结论比"修了个 bug"更有价值。

---

## 一、SSE 与流式（5 个）

### P1. 开一条断线续传，把正在生成的原连接「静默踢掉」

**现象**：用户网络抖一下，页面自动重连；重连成功，但原来那个标签页再也收不到任何事件，既没有 `DONE` 也没有错误，只能一直转圈。更诡异的是并发多条续传时，同一个已完成消息 5 条连接只有 0~3 条拿到内容，90% 空响应。

**定位**：`channels` 是 `Map<Long, SseChannel>`，`resume()` 里 `put(messageId, newChannel)` 覆盖旧值并 `close()` 旧连接；而被踢连接的清理又调用 `closeChannel(messageId)`（按 messageId 删），把此刻表里的**最新**连接也关掉——多条连接互相消灭。

**修复**：改成 `Map<Long, Set<SseChannel>>`，同一 messageId 允许多连接并存；清理改为"只注销自己"（带着自己的 `subscriberId`）；轮次结束时向集合里每一条连接发终态。配套把 Pub/Sub 订阅改成"每个 messageId 一份共享订阅 + 引用计数"。

**可复用排查法**：凡是"按 ID 覆盖集合里的元素"的写法，先问自己：**这个 ID 上会不会有多个活着的实体？** 长连接、会话、订阅几乎都是"1 对 N"。另外，任何"清理"函数如果用父 ID 做参数，几乎一定会误删兄弟节点。

### P2. 事件序号出现空洞，续传时丢过程事件

**现象**：断点续传后文字基本对得上，但工具卡片、引用来源这些过程事件会少一两个；客户端日志里 seq 不连续，出现过间隔 34 的空洞。

**定位**：收尾路径用了两个序号来源——生成期间用本地 `AtomicLong`，收尾的 `BLOCKED/DONE` 却用 `streamBuffer.lastSeq(messageId) + 1`（读 Redis）。两条路径并发时各自算出同一个号或跳过号。

**修复**：一条流只允许一个序号来源。把 `AtomicLong sequence` 声明在 try 之外，`START=1`，之后每个事件（含终态、含错误路径）都用同一个 `incrementAndGet()`，彻底删掉"从 Redis 取号"的分支。

**可复用排查法**：**序号/ID 生成必须是单点**。搜索代码里所有 `+ 1`、`max(...)+1`、`lastXxx+1`，只要同一个序列有两个生成点，就一定会跳号。排查时先看"收尾路径"和"异常路径"，它们最容易被写成第二来源。

---

### P3. 一个慢客户端让全实例的续传停摆

**现象**：30 并发完全正常，压测到几百并发时出现"某些用户的回答突然不动了"，但服务端日志没有任何异常。

**定位**：`emitter.send()` 是阻塞写。三类生产者都直接写 socket：生成线程（池上限 64）→ 64 个慢客户端就能让实例停止生成；Pub/Sub 监听回调（默认**单分发线程**）→ 一个慢客户端就能让全实例续传停摆；心跳（4 线程调度器）→ 4 个慢客户端让所有连接心跳停掉。这是典型的队头阻塞。

**修复**：每连接一个 `ArrayBlockingQueue(512)` + 一条虚拟线程写者，生产者只 `offer()`；队列满则丢最旧帧 + 入队 `INTERRUPTED{resumable:true}` + 优雅关闭，**生成本身继续**（完整回答仍落库，重连可补齐）。

**可复用排查法**：看到"某个操作是阻塞写"（socket、文件、stdout、同步日志 appender），就问：**它跑在谁的线程上？那个线程是共享的吗？** 共享线程 + 阻塞调用 = 队头阻塞。修法是"把阻塞搬到每连接/每任务的私有线程"，而不是"加大线程池"。

### P4. 收尾时 `interrupt()` 写入器，终态帧被永久丢弃

**现象**：客户端"流结束了但没有终态事件"，页面停在 streaming；服务端日志干干净净，没有任何异常。压测 1000 并发时每轮有 2~5 个请求命中。

**定位**：`close()` 里直接 `writer.interrupt()`，写者立刻退出循环，队列里还没写出的帧（尤其是 `DONE`）被丢掉。另一半原因：`drainAndComplete()` 在**调用方线程**上轮询同一个队列，与写者形成两个消费者，既有交错写入也会丢末帧。

**修复**：用**哨兵帧**（`Frame.terminator()`）代替 interrupt：`close()` 只入队哨兵并拒绝新帧，写者按顺序写完后自然退出；队列只有写者一个所有者，调用方只负责投递哨兵/关闭信号。`close()` 时把 `pendingBySeq` 里等缺口的帧强制按序刷出，保证终态不会因为等一个永远不来的 seq 而卡住。

**可复用排查法**：**所有"中断/关闭"都要区分语义**：是"放弃"（可以不写完，`abort()`）还是"收尾"（必须写完，`close()`+哨兵）？混用这两个语义，一定会丢数据。判断标准：调用方能否观察到"没写完"。

---

### P5. 看门狗用 `KEYS`：既拖慢全局，又掩盖了一个正确性缺陷

**现象**：1000 并发下完成延迟 P50 高达 14 秒，而 30 并发只有 3.4 秒；把 `KEYS` 换成 `SCARD` 之后性能恢复，但立刻冒出 657 个失败——用户明明连着，回答却被中止。

**定位**：两件事叠在一起。① 订阅者计数用 `redis.keys(prefix + "*")`，Redis 单线程，`KEYS` 会阻塞整个实例并扫全库；看门狗每 5 秒对每个断线消息各调一次。② 看门狗慢到几乎跑不动，反而掩盖了真正的 bug：**初次发起对话的连接从来没登记订阅者**（只有续传路径登记了），看门狗"准时"之后就开始误杀。

**修复**：① 用 `SADD`/`SCARD`（O(1)）替代 `KEYS`；② 初始连接同样登记订阅者；③ 心跳顺带 `EXPIRE` 续期订阅键。

**可复用排查法**：**性能问题和正确性问题会互相掩盖**。修完一个性能瓶颈后，第一件事是重跑全量回归——原来"碰巧没事"的路径会立刻暴露。另外，`KEYS`/`SCAN`/`HGETALL` 这类 O(N) 命令永远不要在请求或定时任务里对全库跑。

## 二、Agent 与 RAG（3 个）

### P6. 用户点了「停止」，拿到的却是「成功但半句话」

**现象**：点停止后，回答停在句子中间，但状态是 `DONE` + 落库 `COMPLETED` + 审计 SUCCESS。实测正文只有 96/345 字。

**定位**：`stop()` 只写 Redis 取消标记，模型回调看到标记就丢弃后续 token——但**没有任何东西去终结这一轮**。终态仍然由"模型自然收流"的 `onCompleteResponse → finishSuccessfully` 写出，于是系统认为一切正常。

**修复**：`stop()` 不再只打标记，而是直接执行**中止钩子**：在轮次锁下立刻收口为 `INTERRUPTED`，保留已生成内容、明确标记、审计记 `AGENT_TURN_STOPPED`，原因串写"用户主动停止生成"（绝不借用超时文案）。轮次锁用 `ReentrantLock` 而不是 `synchronized`——收口路径有 DB/Redis 往返，虚拟线程上 `synchronized` 会 pin 住载体线程。

**可复用排查法**：**"停止"必须是一个终结动作，不是一个过滤器。** 任何"取消"实现都要回答：谁负责把状态写成终态？如果答案是"等它自然结束"，那用户拿到的永远是"成功但残缺"。

---

### P7. 空回答被当成成功（604 条 COMPLETED 里 32 条正文为空）

**现象**：用户看到一个"成功但空白"的气泡：没有内容、也看不出失败，只能反复重问。占比 5.3%。

**定位**：两条路径都会在 `answer` 为空时写 `COMPLETED`——正常收尾 `finishSuccessfully` 和"工具往返超限优雅收口"分支。弱模型反复调工具直到撞上限、却没产出任何正文，就是典型场景。

**修复**：把"非阻断且正文为空"明确记为 `FAILED`，并给可读原因；判空要带上 `guard.finish()` 的尾窗文本（最后一段增量可能只在 tail 里）。注意：空正文的**终态事件仍是 `DONE`**（payload 里 `status=FAILED`），排障时要看 `status`，不能只看事件名。

**可复用排查法**：**"成功"的定义要显式写出来**。像"有产出"这种隐含前提，一定要落到代码里的判定条件，否则统计上永远是"成功率 94.7%"这种自欺欺人的数字。

---

### P8. RAG 有命中，但前端引用永远是 0、刷新后来源消失

**现象**：`ragHits > 0`，但 SSE 的 `REFERENCE.count = 0`；历史消息接口没有 `references` 字段，刷新页面后来源列表全空——正文写着"根据某制度"，却拿不出来源。

**定位**：两个独立原因。① 早期只在 LangChain4j 的 `onRetrieved` 回调发 REFERENCE，而工具式 RAG 根本不走这个回调；② 引用只在 SSE 里发过，没有随消息落库。

**修复**：`PolicyTools` 把命中写进 `AgentTurnContext.references`（按 title+snippet 去重、上限 20 条）；收尾前统一发一次 REFERENCE；随消息落库到 `agent_message.references_json`（`V4__agent_message_references.sql` 是配套迁移），历史接口一并返回。

**可复用排查法**：**"实时链路"和"历史链路"必须由同一个数据源驱动**。只做实时、不做持久化，用户一刷新就露馅；反过来只落库不推实时，用户要等回答完才看到引用。排查时对比"刚生成时"和"刷新后"两个视图，差异就是缺口。

## 三、数据、权限与一致性（4 个）

### P9. 统计接口越权：员工看到的是全库数字

**现象**：普通员工打开统计看板，`TOTAL=335/50`，和总管理员完全一致；而同一个人的分页列表接口 `total=38` 是对的。

**定位**：分页列表逐个补了区域条件，统计接口是"另写一遍"的查询，没补。更根本的是模型错了：员工被当成"按本区域过滤"，正确语义是"只看自己的数据"——`visibleRegionId()` 对员工返回的是他的区域，用它过滤业务量必然看到本区域的全部人。

**修复**：新增 `DataScope.statisticsScope()` 作为统计粒度的唯一收口点：员工 → `employeeId=自己`；区域管理员 → 本区域；总管理员 → 不限；**账号未分配区域 → 直接拒绝**（原来是 `regionId == null ⇒ 不加条件`，一个没分配区域的管理账号会静默看到全库，fail-open 比报错可怕）。

**可复用排查法**：**权限是"每个入口 × 每种粒度"的矩阵**，不是一张开关。发现一个越权点后，立刻按入口清单（列表/详情/导出/统计/聚合）逐个对一遍。凡是 `if (x == null) 不加条件` 的写法，默认当作漏洞审查。

---

### P10. 页面说「还有 76 张可订」，审批时却报床位被占

**现象**：查房页显示可订，员工提交申请、管理员审批时大量 3005（床位占用）；实测宣称可订 76 张、实际可分配 59 张。

**定位**：读路径按"日期区间不重叠"算可订数，写路径 `occupyBed` 只看 `WHERE status='IDLE'`——两者不等价。另一种情形更糟：不传日期时，`NOT EXISTS` 整段被 `<if>` 丢掉，`available_beds` 退化成"非 DISABLED 计数"，把已占用的床也算成可订。

**修复**：`available_beds` 的定义与写路径**逐字等价**（此刻 IDLE 床位数）；日期维度的信息保留在 `bookable_beds` 字段，明确标注"仅作提示"；用派生表避免 `GROUP BY/HAVING` 与 `ONLY_FULL_GROUP_BY` 打架。

**可复用排查法**：**读路径的承诺必须能被写路径兑现**。对比"查询条件"和"更新条件"是不是同一组；不是的话，要么改读、要么改写的语义，不能靠"用户点下去再报错"来兜。

---

### P11. 幂等检查放在限流之后：花的是重试的钱，拦的是真实的提问

**现象**：客户端网络抖动时重试同一个 `turnId`，几次之后真正的提问被限流拒绝（6001），用户以为系统坏了。

**定位**：幂等预检排在第 6 步（限流/预算/并发之后）。纯重放不调模型、不占生成资源，却每次都白扣一个令牌——连续重放几次就把 20 次/分钟的配额吃光。

**修复**：幂等预检提到**最前面**（护栏之后、限流之前），命中直接重放既有回答、不占任何配额。重放路径也**不递减**并发计数（它从未 increment，递减会让计数变负，反而放宽别人的上限）。另一半是并发场景：MySQL RR 下旧事务快照看不到胜者行，局部回查一直失败（成功率 1/20 → 11/20），最终改成"捕获 `DuplicateKeyException` → **换新事务重试**"，因为 InnoDB 重复键插入会阻塞到胜者提交，新事务必然能看到它。

**可复用排查法**：**准入链路的顺序原则：便宜的先做、不需要资源的先做、能被复用的先做。** 幂等 > 配额 > 资源。另外，凡是在事务里"回查别人刚写的行"，先想隔离级别——RR 下你可能永远看不到。

---

### P12. 检索日志里 user_id / conversation_id 全是 NULL

**现象**：`rag_retrieval_log` 当日 81 行、81 行的 `user_id`/`conversation_id`/`message_id` 都是 NULL，运营看板"点踩 → 当时检索到什么"这条排查链路实际不成立，但代码注释声称已补齐。

**定位**：落库被丢给 `retrievalLogExecutor` 的池线程执行，而 `TraceContext`/`AgentTurnContext` 是 ThreadLocal——池线程里全是空的。同类问题还有：线程池打满时 `CallerRunsPolicy` 把审计写放到模型回调线程上，跟业务请求抢数据库连接（实测 total=128/waiting=192 耗尽）。

**修复**：**在调用线程取上下文快照，作为参数传进异步任务**，不在池线程里读 ThreadLocal；审计/检索日志这类观测数据改为"有界在途 + 超限丢弃并计数"，宁可丢观测数据也不拖死业务。

**可复用排查法**：**看到 `ThreadLocal` 和线程池同时出现，就要怀疑上下文丢失**。三个必查点：`runAs` 是否包住了异步入口、异步任务的参数里有没有显式快照、拒绝策略会不会把任务弹回关键路径线程。

## 四、模型、认证与收尾一致性（4 个）

### P13. 模型流的并发上限其实由 JVM 公共线程池决定

**现象**：配置里写着全局 1000 条并发流，实际到几十条就开始互相拖慢；日志里模型回调线程是 `ForkJoinPool.commonPool-worker-*`。

**定位**：LangChain4j 默认 `JdkHttpClient` 的流式实现是 `sendAsync().thenAccept(...)`，`thenAccept` 在"完成 future 的线程"上执行，JDK 交给 `CompletableFuture` 默认执行器（commonPool；2 核容器退化为 thread-per-task）。整个 SSE 读循环占着这条线程直到 `[DONE]`，每 token 的 Redis 写、护栏、工具 HTTP 也都压在上面。

**修复**：自定义 `VirtualThreadJdkHttpClient`：流式用同步 `jdkClient.send()` + 专用虚拟线程（`agent-model-stream-*`）；非流式继续委托官方 `JdkHttpClient`（保持错误映射/multipart/超时一致）。加两条回归：直连 SSE 断言回调线程是虚拟线程；端到端断言 token/完成回调不在 commonPool。

**可复用排查法**：**"并发上限"要问清楚是哪一层的上限**：线程池？连接池？信号量？还是某个你委托的库内部的默认池？排查时打印线程名——线程名是判断"这段代码到底跑在谁的线程上"最便宜的证据。

---

### P14. 同一轮：用户看到 `DONE + COMPLETED`，审计却写 FAILED

**现象**：模型触发"超过 3 次工具往返"后优雅收口，SSE 发的是 `DONE + COMPLETED + graceful=true`，`audit_log` 却是 `AGENT_TURN_FAILED`——"用户看到的"和"审计记录的"不一致，事后分析直接跑偏。

**定位**：收口路径只按"是否抛异常"决定审计结果，没有区分"异常但已优雅交付部分结果"这一种状态；同时 `cost_ms`、`model`、`tokens`、`toolCalls`、`ragHits` 在异步审计改造中丢了。

**修复**：统一成 `AGENT_TURN_DEGRADED`（`result=SUCCESS`）并带降级明细（`status/graceful/toolCalls/ragHits/partialLength`）；审计接口接收 `detail` 与 `costMs`，恢复实测 `cost_ms=8517`；审计改为虚拟线程异步提交，捕获 token/trace 快照，不阻塞 `DONE`。

**可复用排查法**：**终态一致性要三方对齐**：SSE 终态事件、消息表状态、审计 action。任何一方独立判断"成功/失败"都会漂移。上线前用一张"失败与终态矩阵"（`docs/agent-sse-design.md` §9.3）逐格对一遍，比事后查日志便宜得多。

## 附：如果只记一条

> 这 17 个坑的共同模式是：**同一种信息存在两个来源**（两个序号源、两个连接表、读口径 vs 写口径、实时 vs 落库、看到的 vs 审计的、线程 vs ThreadLocal）。
> 架构上能做的唯一防御是：**给每一种状态指定唯一权威**，其余全部派生。这也是这个项目里"单一来源"反复出现在 seq、状态机、`ToolCatalog`、`DataScope`、`RedisKeys` 上的原因。

### P15. 看板出现「开放房间 265 / 房间总数 136」：JOIN 放大了 COUNT

**现象**：管理端看板卡片显示「开放 265、关闭 12、维修 0」，而同一行的「房间总数」是 136——开放数比总数还大，一眼就是错的。

**定位**：`DormRoomMapper.statisticsByRegion` 为了同时统计床位，`LEFT JOIN dorm_bed` 之后再 `SUM(CASE WHEN r.status = 'OPEN' THEN 1 ELSE 0 END)` 数房间。JOIN 后一行房间会变成 N 行（N=床位数），`SUM` 于是把「一房两床」算成 2 间。`COUNT(DISTINCT r.id)` 因为加了 DISTINCT 没被放大，所以只有状态分项错、总数对，差异只体现在分项上，更不容易被发现。

**修复**：三个状态分项统一改成 `COUNT(DISTINCT CASE WHEN r.status = #{S_OPEN} THEN r.id END)`，并在 SQL 里写了注释说明「JOIN 之后不能直接 SUM 房间数」。

**可复用排查法**：**只要聚合查询里有 JOIN，就问一句"这一行到底是几行"**。判断口诀：维度表用 `COUNT(DISTINCT 维度主键)`，事实表才能用 `SUM/COUNT`。上线前加一条校验断言（分项之和 = 总数），比看板做兜底文案便宜。

### P16. 状态标签的文字看不见：同色叠同色

**现象**：列表页「待审批 / 已通过 / 已入住 / 已退房 / 已驳回」渲染成一排纯色小色块，文字完全消失。截图工具量出来的 computed style 是：背景 `rgb(64,158,255)`、文字 `rgb(64,158,255)`。

**定位**：组件把「状态色」当成背景色（`el-tag :color`），同时又用同一个颜色给内部 `span` 设置文字色；`effect="light"` 本意是浅色底，但显式 `color` 覆盖了默认浅底，于是变成饱和色底 + 同色文字。另外有 4 个页面没走统一组件，各自手写了同样的 `el-tag + span` 组合，所以修一个组件修不全。

**修复**：`StatusTag` 的 light 效果改为「同色 10% 透明度做背景（`#RRGGBB1A`）+ 原色文字」；4 个手写页面统一成同一写法。顺带把状态文案与颜色全部收口到 `/api/meta/enums`，不再硬编码。

**可复用排查法**：**色彩对比度不能靠肉眼，靠 `getComputedStyle`**。UI 验收脚本里加一条断言：标签背景与文字色的对比度 ≥ 3:1（或至少 `bg !== color`），几十行代码就能拦住这类"截图上才看得见"的问题。

### P17. 运营看板两处「静默错误」：字段大小写不匹配 + 隐藏 tab 里的图表

**现象**：
1. 「用量趋势」tab 的 x 轴显示 `undefined`，画布挤在左边约 200px；
2. 「工具调用统计」表的「工具」列全空、「平均耗时」只剩一个 `ms`；
3. 「知识库索引」的「最近一次加载报告」显示文档数 0 / 片段数 0，而同页「索引片段数」是 110。

**定位**：
1. 前端类型定义写的是 `stat_date / tool_calls / avg_cost_ms`（snake_case），但后端 VO 早已统一驼峰（`statDate / toolCalls / avgCostMs`）。字段名对不上时前端拿到的都是 `undefined`——**不会报错，只会显示空白**，属于最隐蔽的一类 bug；
2. ECharts 在 `display:none` 的 tab 容器里初始化，容器宽度为 0，echarts 退化成默认宽度并让坐标轴错位；
3. 同一个前端类型里把 `lastLoadReport` 写成 `documents / chunks`，而接口返回 `documentCount / chunkCount`。

**修复**：
1. 把 `ui-service/src/api/types.ts` 里这三组类型改成与后端 VO 一致（并删掉那条「后端为 snake_case」的错误注释）；
2. 切到「用量趋势」tab 时 `nextTick` 后 `resize()`，没初始化过就补一次渲染；
3. 去掉恒为 0 的「索引大小」行，索引规模以顶部 `indexSize` 为准。

**可复用排查法**：
- **前后端字段名要有一处"唯一真相"**：能共享契约就共享（本项目后端有 `dorm-contract`），不能共享就在类型文件里注明来源 VO 的类名；
- **看 UI 有没有"空白但不报错"的列**：接口返回有值、页面是空，先怀疑字段名；
- **图表进 tab/折叠区要 resize**：`display:none` 容器里 init 一定拿不到宽度，切到可见时补 `resize()` 是标准动作。
