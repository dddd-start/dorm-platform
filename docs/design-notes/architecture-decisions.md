# 关键架构决策（11 条）

> 每条都按同一结构：**背景 → 备选 → 选择 → 代价 → 被追问怎么答**。
> 读的时候重点看「代价」和「追问」两栏：能说清代价，才说明真的做过这套取舍。

---

## D1. 把单体拆成三个服务，而不是"一个服务 + 一个 AI 模块"

**背景**：拆分前是一个单体，业务、AI、前端产物在同一个进程、同一个库里。AI 侧引入模型、ONNX 向量模型、SSE 长连接之后，两个问题变得不可接受：依赖体积/故障域耦合（AI 启动要加载向量索引、业务发版要带 183MB 的 Agent jar），以及数据所有权模糊（两个模块都能写同一批表）。

**备选**
- A. 保持单体，只做模块化分包；
- B. 拆成微服务全家桶（注册中心 + 网关 + 配置中心 + MQ）；
- C. 只拆三个进程，共享契约 jar，不引入中间件。

**选择 C**。理由：
1. 服务边界不是"按技术分层"划，而是按**数据所有权**划：`dorm-service` 是业务唯一写入方，`agent-service` 只写自己的 `agent_db`，`ui-service` 不持有状态（见 `docs/architecture.md` §3）。
2. 不引入注册中心/MQ：服务地址用环境变量，Agent 的事件是"单条流的实时 + 历史"，Redis 就够（`docs/architecture.md` §8 明确列了"本阶段不做"的四件事）。
3. 两个后端只共享 `dorm-contract`（纯数据 + 纯函数，不含 Spring、不含 Mapper），可独立构建、独立 `java -jar`。

**代价**
- Agent 工具每次调用多一次 HTTP 往返（`docs/migration.md` §3 记为"有意差异"）；
- 跨服务写没有 Outbox/Saga：Agent 建申请成功、但本地工具审计写失败时，两边不会自动补偿（这是拆分**引入**的缺口，`docs/parity.md` §6 有记录）；
- 共享 Redis 成了新的单点：Redis 挂 → 登录 fail-closed + Agent 流不可用。

**追问「那你为什么不干脆上微服务全套？」**
> 因为规模不匹配。注册中心和 MQ 解决的是"几十个服务、大量异步解耦"的问题，我这里只有 3 个进程、1 个异步需求（事件流）。加进来只会多两个要运维的组件、多一圈排障路径。我把"不引入"写在架构文档里，是为了以后真需要时能说清是增量补，而不是推翻现在的边界。

## D2. Agent 不直连业务库，业务读写全部走 HTTP + 双令牌

**背景**：单体时代 Agent 工具直接注入 `RoomService`、`ApplyService`。拆开后最省事的做法是让 Agent 也连 `dorm_db` —— 那等于"换了个启动方式的单体"。

**备选**
- A. Agent 连业务库（只读账号）；
- B. Agent 直连库 + 业务服务写；
- C. Agent 完全不连业务库，读写都走 `/internal/**`。

**选择 C**。三条具体理由：
1. **表结构变更不会同时炸两个服务**；
2. **权限不绕过收口点**：床位占用、状态机、数据权限、审计只在 `dorm-service` 执行一次；
3. **身份不是声明的**：工具调用带 `Authorization: Bearer <用户JWT>` + `X-Internal-Token`，`InternalAuthInterceptor` 先校验服务令牌，再**重新解析 JWT 并查会话白名单/epoch**，最后 `UserContext.set()`。Agent 无法伪造 userId。

**代价**
- 每次工具调用几十毫秒额外延迟；
- 工具调用是阻塞 HTTP，跑在模型流的虚拟线程上，压测时要盯 pin 风险（`docs/parity.md` §6.3）；
- `dorm-service` 不可用时工具全部失败——这是刻意的：宁可告诉用户"业务服务暂时不可用"，也不让模型拿旧数据编造（`docs/architecture.md` §5）。

**追问「为什么两道令牌，不能只留一道？」**
> 只留用户 JWT：浏览器也能直接打内部接口，攻击面变大。只留内部令牌：Agent 可以随便声明 userId 越权。两个同时校验才同时成立两个命题——"调用方是可信服务"且"代表一个真实、未吊销的用户"。内部令牌用 `MessageDigest.isEqual` 做常量时间比较，生产建议再叠 mTLS。

## D3. 数据权限放在业务服务，并且统计口径单独收口

**背景**：越权漏洞几乎都来自"某个查询忘了加区域条件"。更隐蔽的一类是：分页列表补了条件，统计接口另写一遍没补——实测普通员工在统计页看到的是全库数字，和总管理员一模一样。

**备选**
- A. 每个 Service 自己加区域条件；
- B. 用 MyBatis 拦截器自动拼 SQL；
- C. 一个显式的 `DataScope` 组件，所有入口必须调用它。

**选择 C，并且区分「可见区域」与「统计粒度」两个概念**：
- `visibleRegionId()`：总管理员返回 null（不限），其他人返回自己的区域；
- `statisticsScope(requestedRegionId)`：**员工返回 `employeeId=自己`**（不是本区域），区域管理员只看本区域，区域为空时**直接拒绝**而不是不加条件。
- 这个方法刻意集中在一个类里，`docs/parity.md` 之外没有第二份统计过滤逻辑。

**代价**
- 需要纪律：新写的查询必须调用它，漏了不会编译失败。所以把注释写在方法头上，说明"为什么不能只靠 `visibleRegionId()`"（员工用它过滤业务量会看到本区域所有人的数字）。
- 未分配区域的区域管理员会看到一个明确的 403，而不是"什么都能看"——这是 fail-closed 的体验代价。

**追问「怎么保证以后不写漏？」**
> 三个手段：一是只有这一个类提供行级范围，评审时盯这一处；二是把已发现的漏洞写进文档和注释（`DataScope.statisticsScope` 的注释里就写了 H7 的实测数字）；三是回归里覆盖"员工统计 vs 管理员统计"的差值断言。诚实说：没有编译期强制，这是设计上的已知弱点。

## D4. SSE 断点续传用 Redis Stream + Pub/Sub 双通道

**背景**：SSE 是单向下行。网络抖一下、手机切后台、用户刷新，连接就断。要么重问一遍（浪费 token、内容重复），要么能续传。

**备选**
- A. 只用 Pub/Sub：断线期间的事件**永久丢失**；
- B. 只用 Stream：要么轮询（实时性差），要么 `XREAD BLOCK` 占一条阻塞连接（每轮对话占一条）；
- C. 两者结合：Stream 保历史，Pub/Sub 保实时，seq 保证交接处不重不漏。

**选择 C**，并且写死三条不变量（`docs/agent-sse-design.md` §0）：
1. **seq 单调唯一**，一条流只有一个序号来源（`AtomicLong sequence`，从 START 的 1 开始）；
2. **先写 Redis 再投递**：先 `XADD`（可续传）再 `PUBLISH`（实时），投递失败不影响续传；
3. **生产者永不阻塞**：生成线程/Pub-Sub 回调/心跳只入队，写 socket 由每连接一条虚拟线程负责。

**代价**
- 每个 token 至少 2 次 Redis 往返（`XADD` + `PUBLISH`）；TRIM/EXPIRE 每 20 帧做一次，把每 token 从 4 次往返降到约 2 次；
- 事件会重复投递，客户端必须按 seq 去重（`if (frame.id <= lastSeq) return`）；
- 需要额外维护 6 类键（历史/频道/订阅者/状态/取消/计数），运维面变大。

**追问「为什么不能先拉历史再订阅？」**
> 那两步之间有窗口：这段时间产生的 token 既不在历史里（拉的时候还没写进去），也收不到（订阅还没生效），永久丢失。表现是"文字没丢、过程事件丢了"——序号出现空洞。所以顺序必须是：**先订阅（回调只缓存）→ 补历史 → 切实时 → 按 seq 冲洗缓存**。

## D5. 模型流跑在专用虚拟线程，自己写 HTTP 客户端绕开 commonPool

**背景**：LangChain4j 1.22 的 `OpenAiStreamingChatModel` 默认走 `JdkHttpClient`，实现是 `sendAsync(...).thenAccept(parser::parse)`。`thenAccept` 在"完成 future 的线程"上执行，JDK 把它交给 `CompletableFuture` 的默认执行器：`ForkJoinPool.commonPool()`；2 核容器上 `common.parallelism == 1`，退化成 thread-per-task。**整个 SSE 读循环占着这条线程直到 `[DONE]`**。

**后果**：聊天并发数不再由 `max-streams-global`/`max-concurrent-calls` 决定，而由 JVM 公共池决定；每 token 的 Redis 写、护栏、工具 HTTP 也压在这批线程上。30 并发看不出来，1000 并发就是"把容器 hang 住"。

**备选**
- A. 调大 `commonPool` 并行度（`-Djava.util.concurrent.ForkJoinPool.common.parallelism`）：治标，且公共池被其它代码共用；
- B. 自己开平台线程池：回到"每线程 1MB 栈"的老问题；
- C. 实现一个 `HttpClient`：流式用同步 `send()` + 专用虚拟线程；非流式继续委托官方 `JdkHttpClient`。

**选择 C**（`VirtualThreadJdkHttpClient`）：流式读循环、SSE 解析、LangChain4j 回调全部落在 `agent-model-stream-*` 虚拟线程上；非流式保持官方实现，错误映射/multipart/超时行为不变。

**代价**
- 多维护一份 HTTP 客户端实现，LangChain4j 升级时要跟；
- 唯一的流式入口只支持 JSON（multipart 明确抛 `UnsupportedOperationException`）；
- 90 秒收口**无法强杀**读线程——和官方实现相同的取舍，要"立即取消"得把 `InputStream` 暴露出来 close。

**追问「你怎么证明它真的不在 commonPool？」**
> 两条回归测试：`VirtualThreadJdkHttpClientTest` 直连一个 SSE 服务，断言回调线程名是 `agent-model-stream-*` 且 `isVirtual()`；`StreamingChatModelCallbackThreadTest` 端到端构造 `OpenAiStreamingChatModel`，断言 token/完成回调线程不是 `ForkJoinPool.commonPool` 的 worker。这类"线程归属"问题只能靠断言钉住，靠看日志会漏。

## D6. 每条连接一个有界队列 + 一条写者虚拟线程（write-behind）

**背景**：改造前，生成线程、Pub/Sub 监听回调、心跳任务都直接 `emitter.send()`，而它是**阻塞写**。客户端不读时 TCP 窗口填满，写线程就卡住——队头阻塞：64 个慢客户端能让整个实例停止生成；Pub/Sub 默认单分发线程，**一个**慢客户端能让全实例的续传停摆；心跳共用一个 4 线程调度器，4 个慢客户端能让所有连接心跳停掉。

**备选**
- A. 加大线程池/超时：只是把阈值往后推；
- B. 丢弃慢客户端（直接 close）：会静默截断，用户不知道要重连；
- C. 每连接一个 `ArrayBlockingQueue(512)` + 一条虚拟线程写者，生产者只 `offer`。

**选择 C**，并明确「队列满了怎么办」：
1. 丢弃最旧的一帧腾位置；
2. 入队一个 `INTERRUPTED{resumable:true}` 帧，告诉客户端"你读得太慢，请带 lastEventId 重连"；
3. `close()` 拒绝新帧，让写者把队列里已有的帧**写完**再关；
4. **生成本身继续**，完整回答仍落库，重连即可补齐。

**收尾用哨兵，不用 `interrupt`**：早先直接 `writer.interrupt()` 会让写者立刻退出、队列里未写出的帧（尤其是 `DONE`）被永久丢弃——服务端日志干干净净，客户端"流结束了却没有终态事件"，压测 1000 并发时每轮 2~5 个请求命中这个竞态。

**代价**
- 内存上界 = 连接数 × 512 × 单帧大小，1000 连接时需要按帧大小估算（这是刻意可算的）；
- 多一层间接：出问题的表现从"写阻塞"变成"队列溢出"，必须把 `droppedFrames`/`suppressedDuplicates` 暴露出来，否则变成静默降级。

**追问「为什么用虚拟线程，不用线程池？」**
> 1000 条连接就是 1000 个写者，平台线程每个约 1MB 栈，仅栈就要 1GB——这正是"人一多容器就挂"的直接原因。虚拟线程栈在堆上、按需增长，1000 个写者的开销从"GB 级"降到"几十 MB 级"。而真正的并发上限由业务层的 Redis 计数（每用户 3 / 全局 1000）把守，不该由本地线程池把守。

## D7. 一条消息允许多条连接并存（`Set<SseChannel>` 而不是单值）

**背景**：原实现 `Map<Long, SseChannel>`，等价于"同一条消息只允许一条连接"。两个灾难性后果：
- `resume()` 里 `put` 覆盖旧值并 `close()` 旧连接 → 开一条续传会**静默踢掉正在生成的原连接**，原连接收不到任何终态，用户分不清"正常结束"和"我被踢了"；
- 被踢连接的清理按 `messageId` 删除 → 关掉此刻表里的**最新**连接 → 多条连接互相消灭（实测同一已完成消息并发 5 条续传：0~3/30 拿到完整内容，90% 空响应）。

**选择**：`Map<Long, Set<SseChannel>>` + 每条连接只清理自己 + 轮次结束时向集合里**每一条**连接发终态。

**配套细节**（这些才是真功夫）：
- 订阅按 messageId **共享一份** + 引用计数，最后一条连接关闭才真正退订——否则会踩到 `RedisInvalidSubscriptionException`（实测 HTTP 500）；
- `SseChannel` 用 `pendingBySeq` 按 seq 重排：直投 seq=10 晚于 Pub/Sub seq=11 也不会丢内容；
- `localSubscriberIds` 也是 Set，每条连接只移除自己的 ID——不然会把其它仍在线连接的订阅键续期"遗忘"，看门狗 30 秒后误杀。

**代价**：状态从"一个连接"变成"一组连接"，`compute`/快照遍历/幂等清理都要小心；代码复杂度明显上升。

**追问「为什么要支持多连接？用户不是只有一个页面吗？」**
> 因为断线重连时旧连接不一定立刻消失：TCP 半开、代理超时、切后台，都可能让服务端还留着旧连接。如果新连接必须踢掉旧的，就会出现"重连成功但收不到终态"。多连接并存让每条连接各自独立收尾，代价是注册表和清理逻辑更复杂——我认为这个代价必须付。

## D8. RAG 以「工具」形式接入，而不是 `contentRetriever`

**背景**：LangChain4j 有内置的 `contentRetriever`，在每轮请求前自动检索并拼进上下文。

**备选**
- A. `contentRetriever`：自动、省事；
- B. 工具式：把 `searchDormPolicy` 暴露成 `@Tool`，模型自己决定查不查、查什么、查几次。

**选择 B**。理由：
1. 模型可以判断"这句话需不需要查制度"——寒暄和查自己订单不需要检索；
2. 命中结果进入对话上下文，后续追问能引用；
3. 检索自然带上工具审计、去重、熔断；
4. 区域过滤可以按**本轮用户所在区域**动态拼参数，而不是把过滤器写死在检索器里。

**代价（真实踩过的两个坑）**：
- 工具式 RAG **不走** `onRetrieved` 回调，早期只在 `onRetrieved` 发 `REFERENCE`，结果工具检索时前端永远 `count=0`；
- 引用不落库，刷新页面后来源全部消失。
修法：`PolicyTools` 把命中写进 `AgentTurnContext.references`（按 title+snippet 去重，上限 20 条），收尾时统一发 `REFERENCE` 并随消息落库到 `agent_message.references_json`，`V4__agent_message_references.sql` 是配套迁移。

**检索质量本身**：本地 BGE-small-zh（ONNX 内嵌、512 维、不出网）→ 候选池 = topK×2 且至少 +4 → 区域过滤（本区域 + 全局）→ MMR 重排（λ=0.7）。MMR 解决的是"同一段话被切成 3 个相邻切片占满 Top3"的问题，λ 在"别漏重点"和"别重复啰嗦"之间取经验值。

**追问「为什么不微调/为什么不用大模型 embedding？」**
> 微调解决的是"领域表达不匹配"，我现在的知识库只有 10 篇制度文档、百级切片（实测值见 `/api/agent/admin/knowledge`），样本量根本不够微调，先做的是检索链路可观测：每次检索落 `rag_retrieval_log`（命中数、最高分、耗时、是否缓存命中），能算出无命中率、平均最高分、用户点踩率，并能反查"哪些问题一条都没检索到"——那是知识库的缺口清单。等数据够了再谈微调。

## D9. 意图路由：关键词优先、模型兜底，而不是全交给模型

**背景**：5 个专家 Agent（房源/政策/申请/订单/运维），每轮要选一个。

**备选**
- A. 全部交给模型判断；
- B. 全用关键词；
- C. 关键词打分 + 低分才问模型 + 兜底。

**选择 C**（`AgentRouter.route()`）：
1. 关键词加权打分，最高分 ≥ 6 直接用——确定、即时、零成本；
2. 否则调快模型输出一个类别词，解析失败就回退、**不抛异常**；
3. 再不行兜底 `ROOM`（挂了最全的查询工具）。

**代价**
- 关键词表要人工维护，新业务词覆盖不到时会多一次模型调用（有成本，但只在低分时发生）；
- 两套判定逻辑需要一致的心智模型，改关键词表可能改变路由分布，要观察。

**追问「为什么不全部交给模型？」**
> 两个原因：一是每轮多一次调用，几百毫秒和一份成本，用户只是问"还有房吗"也要付；二是**不稳定**——模型可能这轮判"房源"、下轮把同样的话判"政策"，而路由结果会切换整套系统提示词和工具子集，用户会觉得助手"精神分裂"。关键词的弱点是覆盖有限，所以我保留模型兜底，只是把它放在第二层。

## D10. 把「容器并发」与「上游并发」解耦：候选链 + 熔断 + 闸门

**背景**：只有 `max-streams-global=1000` 时，每一条并发流都会**立刻**向上游发一次模型调用——把容器上限当成了上游配额。实测结果是全链路 429、日志里 490 次 429 与 482 次熔断，熔断又触发降级链在多个模型间来回切换，进一步放大调用量。

**三层设计**：
1. **候选链**：`routing[type] → fast → primary → fallback…`，每个请求拿到有序列表；
2. **调用级降级**：`FailoverStreamingChatModel` 在**每次真实调用周围**切换，而不是"选择阶段"——否则主模型 429 时只会把错误抛给用户，备用模型一直闲着。**只在还没吐出任何 token 时切换**：已经产出内容后换模型重来，用户会看到两段拼接的回答，比明确失败更糟；
3. **闸门**：`ModelConcurrencyGuard` 是 `Semaphore(16)`（`model.max-concurrent-calls`），最多等 8 秒，拿不到就用**业务可读的提示**快速失败（"当前咨询人数较多"）。

**熔断参数**：模型连续失败 2 次 → 熔断 30 秒（`breaker-failure-threshold` / `breaker-half-open-seconds`），半开探测成功即恢复；工具是连续失败 5 次 → 熔断 60 秒（`GuardedToolProvider`）。

**一个必须自己先说的现状**：`candidateChain()` 会去重，而当前 `application.yml` 里 primary / fast / fallback 填的是**同一个型号**（`deepseek/deepseek-v4.1-flash`，注释写明是因为原定备用模型的下线/套餐问题）。所以现在这套机制的真实效果是"同一模型的顺序重试 + 熔断"，**不是跨模型容灾**。要真正做跨模型，改配置即可，代码路径不用动——但别说成"已经做了多模型容灾"。

**代价**
- 闸门拒绝会真实地拒绝用户（虽然不扣额度）——这是"快速失败优于排队"的取舍：排队会把延迟拉到不可接受，且排队期间连接/内存/虚拟线程都占着；
- 降级链让"这次用的哪个模型"变成运行时状态，必须把 `model` 写进 SSE 的 `DONE` 和审计，否则"回答质量变差"时无法归因；
- 候选链去重后可能只剩一个模型（见上），此时"降级"退化为同模型重试，观测上要靠 `degraded` 标志与熔断计数区分。

**追问「熔断和限流的区别？」**
> 限流是"你来得太快"，按配额拒绝；熔断是"它已经坏了"，按失败率跳过一个依赖。我这里限流是 Redis 令牌桶（20 次/分、突发 5），熔断是模型/工具级的连续失败计数。两者都做，是因为 429 和"依赖坏了"要用不同的话术告诉用户：前者让他稍等，后者要触发降级。

## D11. 认证：JWT 无状态 + Redis 会话白名单 + auth epoch

**背景**：纯 JWT 的问题不是"能不能验签"，而是**吊销**：禁用账号、重置口令、改角色/区域、强制下线，必须在**已签发令牌的有效期内**立即生效。

**备选**
- A. 纯 JWT（无状态，吊销不了）；
- B. JWT + 会话白名单（能精确删单个会话，但无法表达"这个用户所有旧令牌作废"）；
- C. 白名单 + 版本号（epoch）。

**选择 C**：
- 登录写 `dorm:auth:session:{userId}:{sid}`（TTL = 令牌寿命），并读/写 `dorm:auth:epoch:{userId}`；
- 令牌里带 `sid` + `epoch`；每个请求 `MGET` 一次取两个键（**一次往返**），会话键不存在 → 401，epoch 不匹配 → 401；
- 吊销全部会话 = `INCR epoch`，无需枚举、无需 SCAN、无竞态。

**三个 fail-closed 细节（都是踩出来的）**：
1. 没有 `sid` 的令牌一律无效。原实现是 `sessionId == null → return true`（fail-open）：带正确签名但去掉 `sid` 的令牌**永远无法被吊销**，登出删不掉、禁用拦不住。
2. 令牌里没有 epoch（本次上线前的旧令牌）→ 拒绝，要求重新登录。
3. Redis 异常 → 拒绝（只记 ERROR 不抛 500）：读不到吊销状态恰恰是最需要保守的时刻。

**启动补偿**：上线前就被禁用的账号，旧令牌 epoch=0、Redis 无键（缺省 0），两边相等会放行。所以启动时用 `setIfAbsent` 给这些账号把 epoch 抬到 1——**必须用 `setIfAbsent`**，绝不能把已递增的版本降回去（会让已吊销的令牌复活）。

**代价**
- 每个请求多一次 Redis 往返（两个服务都要）；
- Redis 成了认证链路上的硬依赖：Redis 挂 = 所有人 401。这是有意的安全取舍，不是故障。

**追问「两个服务怎么保证校验结果一致？」**
> 共享同一个 `DORM_JWT_SECRET`（issuer 也一致），共享同一份 Redis 键前缀 `dorm:auth:*`。agent-service 的 `JwtAuthInterceptor` 只验签 + 查会话/epoch，**不签发令牌**；签发只有 `dorm-service` 的 `AuthService.login` 一个入口。所以"登出后 Agent 立即不可用"是同一个键决定的，不需要跨服务通知。
